## ax-k2 (SK Telecom A.X-K2)

`ax-k2/README.md` only points to the docs site. The substantive text is in `docs/.../ax-k2.mdx`, `ax-k2/perf/README.md`, and the per-variant READMEs.

**Model / checkpoint**
- HF ids, from `ax-k2/model-cache/model-download.yaml`, pinned by revision:
  - `skt/A.X-K2-NVFP4` at `--revision 9e2e804e80f8d1b3afba5d7938173cec1ed46b49` (target model)
  - `skt/A.X-K2-EAGLE3` at `--revision 24958e91737d760908f73a8af4b6e06080fc5c1d` (EAGLE3 draft)
- Precision: **NVFP4 weights**. The KV cache is **FP8** (`--kv-cache-dtype fp8`).
- Total and active parameter counts are not stated anywhere.
- Context: `--max-model-len 262144`. The perf README says "A.X-K2 supports a 262,144-token context."
- PVC: `model-cache`, 600Gi, RWX. Download image: `python:3.12-slim` with `huggingface_hub==1.16.4`.
- Attention backend: `FLASHINFER_MLA_SPARSE`. Every variant also sets `--kernel-config '{"enable_flashinfer_autotune": false}'`, `--block-size 64` and `--enable-prefix-caching`.

**Container**: `nvcr.io/nvidia/ai-dynamo/vllm-runtime:1.4.1-a.x-k2-post.1` for both frontend and workers, with `runtimeVersionOverride: 1.4.1`. The benchmark uses `nvcr.io/nvidia/ai-dynamo/aiperf:0.12.0`.

**Parsers** (identical on every worker):
```
--dyn-tool-call-parser hermes \
--dyn-reasoning-parser deepseek_v3 \
--reasoning-parser deepseek_v3
```
No `--enable-auto-tool-choice` and no native `--tool-call-parser`.

**Speculative decoding**: EAGLE3 with 3 tokens, supplied through the ConfigMap key `speculative-config`:
`{"method":"eagle3","model":"skt/A.X-K2-EAGLE3","revision":"24958e9...","num_speculative_tokens":3}`
There is also a benchmark-only key, `speculative-config-synthetic`, that adds `"rejection_sample_method":"synthetic","synthetic_acceptance_length":2.12`.

**Router**: the frontend runs `python3 -m dynamo.frontend --router-mode kv --router-kv-events --kv-cache-block-size 64`. Workers publish KV events with `--kv-events-config '{"publisher":"zmq","topic":"kv-events","endpoint":"tcp://*:20080","enable_kv_cache_events":true}'`. The disagg decode worker has no kv-events config; only prefill publishes. There is no KV offload.

- Workers run as `runAsUser: 0` with the IPC_LOCK and SYS_RESOURCE capabilities.

## deepseek-v4 (family level: README, container/, perf/)

### `deepseek-v4/README.md`
- Tuning target: "**agentic** workload (64k ISL / 400 OSL / 90% KV reuse) at a floor of **≥ 50 output tok/s/user**".
- Sizes: Pro "1.6T / 49B active · 1M ctx"; Pro-0813 "1.6T · 1M ctx"; Flash "284B / 13B active".
- Recommended picks:
  - Pro: B200 → `disagg-b200-agentic`; H200 → `agg-h200-agentic`.
  - Pro-0813: GB200 → `agg-gb200-agentic`; H200 → `agg-h200-agentic`.
  - Flash: B200 → `disagg-b200-agentic` (2P1D); H200 → `disagg-h200-agentic` (4P3D).
- Checkpoints: "B200 variants serve the NVFP4 checkpoints (`nvidia/DeepSeek-V4-*-NVFP4`); H200 variants serve the public checkpoints (`deepseek-ai/DeepSeek-V4-*`). H200 Pro is capped at `max_model_len=86,016` (HBM); B200 and H200-Flash keep the full 1M window."
- Workload table: Agentic 64k/400/90%/≥50; Custom (decode-heavy synthetic) 10k/1k/10%/≥50, Flash only.
- **Per-rank NIC mapping** (disagg only):
  - `VLLM_GPU_NIC_PCIE_MAPPING` and `VLLM_NIC_SELECTION_VARS=UCX_NET_DEVICES:1` must be set as a pair (vLLM #42083). "The recipe ships neither."
  - Without them: "~0.76 GB/s with 4 ranks on one NIC vs ~15–25 GB/s with one NIC per rank (~25× slower)".
  - B200 disagg requests `rdma/shared_ib: "1"`; H200 disagg requests `rdma/ib: "N"`.
  - With `shared_ib`, "a **wrong or stale map fails silently**".
- **Known limitations**:

- Disagg at C=7: "55 tok/s/GPU, but E2E 70.6 tok/s/user and TTFT p50 1,018 ms".

**Caveats** (`k-exaone-2.0/README.md`):

- "**TP=4 is the floor and the optimum.** ~530 GB of weights does not fit TP=2 … TP=8 … is still ~30% slower per GPU".
- "`--block-size 64`. Block size 16 is measurably worse."
- "Spec-dec and block size **must match across prefill and decode** — a mismatch … produces silent garbage output".
- "do not add `--load-format fastsafetensors` without GPUDirect Storage … it stalls before opening a single shard."
- "Use **temperature 0.6, not greedy** — `temperature=0` drives it into rumination."
- "First start takes **40–120 minutes**".
- "The RDMA resource name is cluster-specific" (`rdma/shared_ib`).
- "Verify the KV transport before trusting any disaggregated measurement".
- "No cache-clearing endpoint … `POST /reset_prefix_cache` returns 404".
- "`--enable-prompt-tokens-details` is a `vllm serve` flag and is rejected by `dynamo.vllm`".

## A100 / older-GPU findings (important for the university audience)

1. **`recipes/README.md` claims**:
   - line 35: `| **[Qwen3-32B-FP8](qwen3-32b-fp8/trtllm/agg/)** | TensorRT-LLM | Aggregated | 2x H100/H200/A100 | ...`
   - line 36: `| **[Qwen3-32B-FP8](qwen3-32b-fp8/trtllm/disagg/)** | TensorRT-LLM | Disaggregated | 8x H100/H200/A100 | ...`
   - line 37: `| **[Qwen3-32B-FP8](qwen3-32b-fp8/vllm/disagg/)** | vLLM | Disagg (Single-Node) | 8x A100 | ✅ | ✅ | 2× TP2 prefill + 1× TP4 decode, NixlConnector KV transfer | ❌ |`
   - line 81 (Functional recipes, "Not Yet Benchmarked"): `| **[Qwen3-32B](qwen3-32b/vllm/cloud-providers/)** | vLLM | Disagg 1P1D Provider Overlays | 8x A100/H100/H200/B200/GB200 | ✅ | Kustomize overlays for AWS EFA, GKE RoCE, AKS/Nebius/Nscale IB |`
2. **The only A100-specific change anywhere in the manifests** is in `qwen3-32b-fp8/vllm/disagg/deploy.yaml`: `--max-model-len 8192` on both prefill and decode. `qwen3-32b-fp8/README.md` says: "`--max-model-len 8192` is set in `vllm/disagg/deploy.yaml` for A100 40 GB compatibility; remove or increase this flag on H100/H200". The Fern page `docs/fern/pages/recipes/model-recipes/qwen3-32b-fp8.mdx` repeats this (line 251) and says "8x H100/H200/A100, single node" for vllm/disagg.
3. **How FP8 runs on Ampere (vLLM path)**: none of the recipe files mention Marlin, weight-only, or Ampere. The vLLM disagg manifest does **not** set `--quantization` or `--kv-cache-dtype`, so vLLM auto-detects the FP8 checkpoint config and uses KV dtype `auto` (BF16). I checked the vLLM shipped in the local Dynamo vLLM image (`/tmp/enroot-data-1004/dynamo-vllm/.../vllm-0.23.0`): `quantization/fp8.py` reports `get_min_capability() -> 75` and contains the comment "For GPUs that lack FP8 hardware support, we can leverage the Marlin kernel for fast weight-only FP8 quantization"; `utils/marlin_utils_fp8.py: is_fp8_marlin_supported()` returns `has_device_capability(75)`. So on A100 (SM80) the vLLM recipe runs as **W8A16 FP8-Marlin (weight-only; FP8 weights are dequantized in-kernel, BF16 activations and BF16 KV)**. That gives the memory savings of FP8 weights (~32 GB of weights, ~16 GB/GPU at TP2, ~8 GB/GPU at TP4) but not FP8 tensor-core compute. This is an inference from the vLLM code, not a statement in the recipe.
4. **TRT-LLM on A100 is doubtful** (my assessment, not stated in the repo): both `qwen3-32b-fp8/trtllm/agg/deploy.yaml` and `trtllm/disagg/deploy.yaml` set `kv_cache_config.dtype: fp8` and load the FP8 checkpoint through TRT-LLM's PyTorch backend. TRT-LLM FP8 GEMMs and FP8 KV cache require SM89+ (Ada/Hopper/Blackwell). No A100 override, no alternate config, and no A100 benchmark exists in the repo, so treat the "A100" label on the TRT-LLM rows as unverified.
5. **qwen3-32b cloud-providers**: the A100 mention exists only in `recipes/README.md` line 81 (the `cloud-providers/README.md` and all overlays never mention a GPU SKU; no nodeSelector for GPU product). The workload is BF16 `Qwen/Qwen3-32B` at TP4 per worker (~16 GB weights/GPU) with `--max-model-len 131072` via YaRN; it needs RDMA (IB/RoCE/EFA) for NIXL. Plausible on 8x A100-80GB; the recipe itself is labelled "Functional Recipes (Not Yet Benchmarked)".
6. **qwen3-32b agg-kvbm hardware note** (`qwen3-32b/vllm/agg-kvbm/README.md`): "**1x NVIDIA H200 (141 GB) or B200 (192 GB)**. Qwen3-32B in BF16 is ~64 GB of weights plus KV cache and activations, so 80 GB H100 leaves very little room and is likely to OOM under real load. If you only have H100 80 GB, see `../../../qwen3-32b-fp8/` for the FP8 variant." (Same logic applies to A100-80GB.)
7. **qwen3.6-35b `hw/h100.env`**: single-GPU H100 target for `Qwen/Qwen3.6-35B-A3B-FP8` (35B total / 3B active MoE; FP8 weights ~35 GB). Image `nvcr.io/nvidia/ai-dynamo/vllm-runtime:1.3.0`, `HW_TOLERATIONS='[]'`, nodeSelector is a hostname placeholder `<FILL-IN-H100-HOSTNAME>`. H100 has native FP8. No numbers are published for it. On an A100 this FP8 MoE checkpoint would again need vLLM's Marlin fallback (FP8 MoE Marlin); nothing in the recipe covers that.
8. **Smallest footprints overall**: qwen3-0.6b (1 GPU per replica, any SKU, no SKU pin), qwen3-vl-32b-fp8 agg (1x H100/H200), qwen3-vl-30b (1x GB200 in the published result, no SKU pin in the manifest), qwen3.6-35b (1x H100 or GB200), qwen3.6-35b-a3b (1x H200/B200/GB200), qwen3-32b agg-kvbm (1x H200/B200).

## recipes/accuracy/ (README.md, accuracy.yaml)

**What it does**: a model-agnostic Kubernetes Job (`accuracy-check`) that runs a public benchmark through a deployed Dynamo frontend with AIPerf's accuracy mode and grades the answers. README: "Read the result as an **A/B test**, not an absolute capability claim: A is the score measured through your deployment, B is the checkpoint's published model-card number for the same benchmark." It is explicitly "not a perf benchmark".

**Benchmarks supported** (README + yaml comment): MMLU (`mmlu`), MMLU-Pro (`mmlu_pro`), GSM8K (`gsm8k`), MATH-500 (`math_500`), GPQA-Diamond (`gpqa_diamond`, the **default**), HellaSwag (`hellaswag`), BIG-Bench Hard (`bigbench`), LiveCodeBench (`lcb_codegeneration`), and AIME variants `aime` (2024, 8-shot), `aime24` (2024, 0-shot, "matches most published trt-llm/lighteval numbers"), `aime25` (2025, 0-shot).

**How it is invoked**:
```
kubectl delete job accuracy-check -n $NAMESPACE --ignore-not-found
kubectl apply -f accuracy.yaml -n $NAMESPACE
kubectl logs -f job/accuracy-check -n $NAMESPACE
```
Container `python:3.12-slim`, installs `build-essential` (to build `crick` on aarch64) and `pip install "aiperf[accuracy]==0.12.0"` (the NGC aiperf image lacks the `[accuracy]` extras). It waits on `/v1/models` (up to 720 x 5 s = 1 h), then runs:
```
aiperf profile -m "$TARGET_MODEL" --tokenizer "$TARGET_MODEL" --tokenizer-trust-remote-code \
  --url "http://$ENDPOINT" --endpoint-type chat --accuracy-benchmark "$BENCHMARK" \
  --num-requests "$NUM_REQUESTS" --concurrency "$CONCURRENCY" \
  --extra-inputs temperature:"$TEMPERATURE" --extra-inputs top_p:"$TOP_P" \
  --extra-inputs max_tokens:"$MAX_TOKENS" --extra-inputs max_completion_tokens:"$MAX_TOKENS" \
  --request-timeout-seconds 3600 --random-seed 42 --ui simple --artifact-dir "$RUN_DIR"
```
CONFIGURE block defaults: `ENDPOINT=<your-frontend-service>:8000`, `TARGET_MODEL=<org/model-id>` (must resolve on HF for the tokenizer), `BENCHMARK=gpqa_diamond`, `NUM_REQUESTS=198`, `TEMPERATURE=1.0`, `TOP_P=0.95`, `MAX_TOKENS=100000`, `CONCURRENCY=10`. `activeDeadlineSeconds: 28800` (8 h): "a 198-question run against a large reasoning model at concurrency 10 took ~3.7h". Resources 4-16 CPU, 8-64 Gi. The optional `hf-token-secret` is needed for gated datasets (GPQA). Results are printed and written to `/model-cache/accuracy/<epoch>_<job-name>/accuracy_results.csv` on the `model-cache` PVC.

**What it compares / guidance** (README): compare against the model card at **matched sampling** (temperature, top_p, token limits, and the same quantization); "Harnesses differ ... a small offset from a published number is not by itself a defect"; "One run is not a measurement", so run more than once; "Check `unparsed` first", since a nonzero unparsed count usually means truncation (raise `MAX_TOKENS`); "Remove perf-only synthetic settings from the deployment first" (for example `SGLANG_SIMULATE_ACC_*`, because they bypass draft verification); replica count does not matter (1 replica is enough); raise `CONCURRENCY` to shorten runs.

Related accuracy numbers found in the recipes: qwen3.5-122b fp8 (IFEval 84.66 → 51.02 and GPQA-Diamond 83.84 → 19.19 when `--no-async-scheduling` is missing on the disagg decode worker) and qwen3.6-35b-a3b (GPQA Diamond table in the Fern page, above).

## Key takeaways for the program
1. A100 (Ampere) is officially listed as supported, but current releases (v1.3.0+) ship **CUDA 13 only → host driver ≥ 580** on every GPU incl. A100. If A100 hosts are stuck on driver 575, the newest usable images are `*-runtime:1.2.1` (CUDA 12.9).
2. No documented FP8-on-Ampere guidance; only the Qwen3-32B-FP8 recipe claims A100 compatibility (with `--max-model-len 8192` for A100-40GB). Prefer BF16/AWQ/GPTQ on A100; validate FP8.
3. B300/GB300 need CUDA 13 (fine with 1.5.0 images); B300 is not a DGDR `gpuSku` — profiler/AIC rapid sizing won't cover it.
4. Current release images: `nvcr.io/nvidia/ai-dynamo/{vllm,sglang,tensorrtllm}-runtime:1.5.0` (vLLM 0.28.0 / SGLang 0.5.18 / TRT-LLM 1.3.0rc25); checkout main = 1.6.0-dev.
5. LoRA: use vLLM (Supported); SGLang experimental; TRT-LLM none. KVBM deprecated → use engine-native offload / LMCache / HiCache.
6. Coding agents: Claude Code via `--enable-anthropic-api` (`/v1/messages`, experimental), Codex via `/v1/responses`, OpenCode via chat completions.
7. No Slurm guide; bare-metal multi-node = shared etcd+NATS + per-node worker scripts.
