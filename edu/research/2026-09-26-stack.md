# University GPU Program — Stack Research (as of 2026-09-26)

Research for a program that helps universities with idle GPUs self-host open LLMs on NVIDIA Dynamo, benchmark them, and later post-train their own models.
Every number is tagged with its source. Where NVIDIA quotes only sparse numbers, the dense value is marked as derived (dense = sparse / 2).
Local cross-check: `ai-dynamo/dynamo` main at commit a67b954 (2026-09-21), pyproject `version = "1.6.0"` (dev head).

Notes and caveats:
- **B200 and B300 per-GPU numbers are HGX/DGX 8-GPU totals divided by 8.** Source: HGX page — B300: "FP4 144 PF | 108 PF" (sparse | dense), "FP8/FP6 72 PF", "FP16/BF16 36 PF", "INT8 3 POPS", "FP64 10 TF". B200: "FP4 144 | 72 PF", "FP8 72 PF", "INT8 72 POPS", "FP64 296 TF". The DGX B300 page footnote says "Specification in sparse. Dense is ½ sparse spec shown" for FP8.
- **B300 gains only on FP4 (NVFP4) and attention (2× SFU exponent throughput).** FP8 and BF16 dense match B200. INT8 and FP64 are sharply reduced, so do not plan INT8 W8A8 checkpoints for B300. Use FP8 or NVFP4.
- **RTX PRO 6000 compute:** NVIDIA's page does not say whether the 4/2/1 PF figures are sparse. NVIDIA normally quotes workstation "AI TOPS" with sparsity, so treat dense as roughly half. **Unverified.**
- **RTX PRO 6000 kernels:** sm120 (RTX PRO 6000) and sm121 (GB10) are "Blackwell", but many datacenter-Blackwell kernels are sm100-only (tcgen05/TMEM paths). vLLM has open issues where NVFP4 MoE falls back to Marlin weight-only on sm120/sm121: vLLM #31085, #50925, #54666. Expect lower FP4 efficiency than on B200/B300.
- **DGX Spark:** its 273 GB/s bandwidth makes decode slow (about 1/30 of B200). Use it for small-model development, LoRA fine-tuning up to about 70B per NVIDIA, and demos, not for serving many users.
- **Native precision support** (the "native precision" column above):
  - Ampere has no FP8 or FP4 tensor cores.
  - Ada (L40S) has FP8 but not FP4.
  - Hopper has FP8, and FP4 only through weight-only emulation.
  - Blackwell (sm100/103/120/121) supports FP8, FP6, MXFP4 and NVFP4 natively.

## 2. Serving FP8/FP4 checkpoints on Ampere (A100) and other pre-Blackwell GPUs

**Hardware compatibility table from the vLLM quantization page (https://docs.vllm.ai/en/stable/features/quantization/):**

| Method | Ampere | Ada | Hopper |
|---|---|---|---|
| AWQ | yes | yes | yes |
| GPTQ | yes | yes | yes |
| Marlin (GPTQ/AWQ/FP8/FP4 weight-only kernels) | yes | yes | yes |
| INT8 W8A8 | yes | yes | yes |
| **FP8 W8A8** | **no** | yes | yes |
| bitsandbytes | yes | yes | yes |
| GGUF | yes | yes | yes |

The page footnotes that Turing does not support Marlin MXFP4.

**What works on A100 today:**

1. **FP8 checkpoints (W8A16 via FP8-Marlin).** The vLLM FP8 page says: "Turing/Ampere GPUs are supported for W8A16 (weight-only FP8) utilizing Marlin kernels" (https://docs.vllm.ai/en/stable/features/quantization/llm_compressor/fp8/).
   - Weights stay FP8 in memory, so you keep the ~2× memory saving. They are dequantized to BF16 inside the GEMM.
   - It is a memory-bandwidth win at small batch sizes. There is no compute speed-up, and it can be slower than BF16 at large batch sizes.
   - Dynamo ships a validated recipe: **Qwen3-32B-FP8, vLLM disaggregated, 8× A100** (2× TP2 prefill + 1× TP4 decode, NixlConnector). The recipe sets `--max-model-len 8192` for A100 40GB compatibility. See recipes/README.md and recipes/qwen3-32b-fp8/README.md in ai-dynamo/dynamo.
   - The TRT-LLM Qwen3-32B-FP8 recipes list "2x/8x H100/H200/A100".
   - SGLang has an open feature request for Ampere MoE FP8 through Marlin (https://github.com/sgl-project/sglang/issues/12887). **For FP8 MoE on A100, prefer vLLM.**
2. **MXFP4 (gpt-oss).** The vLLM GPT-OSS recipe says: "GPT-OSS works on Ampere devices by default, using the TRITON_ATTN attention backend and Marlin MXFP4 MoE."
   - gpt-oss-20b runs on one A100.
   - gpt-oss-120b "will fit on a single A100 (80GB)", and TP2/TP4 raises throughput.
   - Source: https://docs.vllm.ai/projects/recipes/en/stable/OpenAI/GPT-OSS.html
   - Caveat: attention runs on the Triton backend, not FlashAttention-3/FlashInfer-TRTLLM, so long-context prefill is noticeably slower than on Hopper.
3. **NVFP4 checkpoints (e.g., nvidia/*-NVFP4) on Ampere/Ada/Hopper.** vLLM loads them through a **weight-only Marlin FP4 fallback** (https://docs.vllm.ai/en/latest/api/vllm/model_executor/kernels/linear/nvfp4/marlin/). You keep the memory saving but get no FP4 compute. Known bugs:
   - Tile-alignment crashes with MoE under EP: https://github.com/vllm-project/vllm/issues/47769
   - MiniMax-M3 NVFP4 produces garbage output on sm90 via Marlin FP4-MoE: https://github.com/vllm-project/vllm/issues/49070
   - Wrong top-k weights at gpt-oss NVFP4 MoE shapes: https://github.com/vllm-project/vllm/issues/48895

   **Treat NVFP4-on-Ampere as best-effort and validate accuracy** (e.g., with NeMo Evaluator or lm-eval).
4. **INT4 AWQ / GPTQ (W4A16) with Marlin kernels** is the most mature low-bit path on Ampere. It is widely available for Qwen and Llama checkpoints and works in vLLM and SGLang.
   - **INT8 W8A8 (SmoothQuant / compressed-tensors)** also runs natively on Ampere INT8 tensor cores (624 TOPS). It is a real compute win for prefill-heavy (agentic) workloads.
   - **Do not use INT8 W8A8 on B300** (INT8 was cut there).
5. **KV cache precision on A100:** there are no FP8 tensor cores, so an FP8 KV cache saves memory only and depends on the backend. Test it before relying on it. BF16 KV is the safe default.
6. **TensorRT-LLM on Ampere:** supported for BF16, INT8 and INT4-AWQ. FP8/NVFP4 in TRT-LLM need sm89+ or sm100+. In Dynamo, TRT-LLM also has **no LoRA support**. **Recommendation for A100 fleets: Dynamo + vLLM backend.**

**Other Ampere caveats:**
- No FlashAttention-3; FA2, Triton or FlashInfer kernels only.
- A100 40GB is very KV-limited for 32K–128K agentic contexts. Use it for ≤14B models or as prefill workers.
- NVLink 600 GB/s on SXM. PCIe A100 nodes without bridges should avoid large TP; prefer DP replicas plus the Dynamo KV router.

### 3.3 NIM vs Dynamo (for universities)

- **NIM LLM 3.0.0** added an opt-in **"Dynamo mode"**: the NIM image ships the Dynamo frontend/router plus independently scaled vLLM workers, set with `DYN_ROUTER_MODE` and related env vars.
  - Dynamo mode requires a vLLM image; SGLang NIM images serve standard mode only.
  - NIM 3.0.0 is **not "NIM Certified"**; use the 2.0 series for certified containers.
  - Sources: https://docs.nvidia.com/nim/large-language-models/3.0.0/about-nim-llm/release-notes.html ; https://docs.nvidia.com/nim/large-language-models/3.0.0/deployment/dynamo-deployment/index.html
- **Multi-LLM NIM** container: auto-selects TRT-LLM, vLLM or SGLang for arbitrary HF checkpoints (https://catalog.ngc.nvidia.com/orgs/nim/nvidia/containers/llm-nim/-).
- **Licensing:** NVIDIA Developer Program members get free downloadable NIM "for development, testing, and research on up to two nodes or 16 GPUs". Production requires NVIDIA AI Enterprise (list price about $4,500/GPU/year). Source: https://developer.nvidia.com/blog/access-to-nvidia-nim-now-available-free-to-developer-program-members/
- **Recommendation:** for a university *research/teaching* program, **open-source Dynamo (Apache-2.0) + vLLM/SGLang is the primary path**. It exposes the internals (router, planner, disagg) that students should benchmark, has no GPU-count cap, and supports day-0 models via recipes. Position NIM as the "packaged, supported" option for campus IT or production-ish services, and note that NIM 3.x can run Dynamo mode.

| **Data Flywheel Blueprint** (NVIDIA-AI-Blueprints/data-flywheel) | v0.3.1 (2025-10-17); **deprecated as of April 2026** ("retained for reference only") | Harvested production logs (Elasticsearch) → NeMo Datastore/Customizer/Evaluator → LoRA / ICL experiments to distill smaller models. Needed 2–6× H100/A100. | **Use as a design reference only.** Re-implement with: Dynamo request-trace sink (v1.5 has an S3 JSONL sink) → Curator/Data Designer → AutoModel/NeMo RL → Evaluator. |

**Recommended lab pipeline for "post-train on coding-agent traces":**
1. Capture traces with Dynamo request tracing (the S3 `RequestTraceSink` writes gzipped JSONL, opt-in) or harness logs (OpenHands, mini-SWE-agent, OpenCode). Consent and PII review are mandatory for student data.
2. Clean with NeMo Curator (dedup, PII), then filter by outcome (tests passed).
3. **SFT/LoRA** with NeMo AutoModel on 1× node (A100/H100 OK) for Qwen3-Coder-30B-A3B / Qwen3.5-9B / Nemotron-3-Nano-30B-A3B.
4. **GRPO** with NeMo RL + NeMo Gym SWE environments. Rollouts run on vLLM; multi-turn with an OpenHands or mini-SWE-agent harness. Plan for ≥2 nodes of H100/H200/B200 for 30B-A3B-class RL; a single node is fine for ≤9B.
5. Evaluate with NeMo Evaluator (SWE-bench Verified/Lite, LiveCodeBench) and serve the adapter via **Dynamo + vLLM dynamic LoRA**. TRT-LLM does not support LoRA in Dynamo.

## 6. Sizing rules of thumb for coding-assistant / agentic users

### 6.1 How agentic coding traffic behaves (published measurements)

- **Dynamo team, "Full-Stack Optimizations for Agentic Inference with Dynamo"** (Mar 2026, updated Jun 2026). Source: docs.nvidia.com/dynamo blog "agentic-inference"; repo file docs/fern/pages/blog/2026/agentic-inference-optimizations.mdx.
  - Claude Code makes "hundreds of API calls per coding session, each carrying the full conversation history."
  - After the first call, subsequent calls to the same worker hit **85–97% prefix cache**.
  - A 42-call session read 891K cached tokens against 76K written: an **11.7× read/write ratio** (write-once-read-many).
  - Agent teams reach a 97.2% aggregate hit rate. Teammates average 79.4% versus 91.3% for explore subagents.
  - System prompt plus tool definitions come to **~32K tokens**.
  - Tool-call pauses of **2–30 s** can let LRU evict the prefix.
  - Compaction takes ~175K tokens down to ~40K.
  - `<think>` blocks are ~40% of generated tokens and are ephemeral.
  - Without KV-aware routing, turn 2 lands on the same worker with probability ~1/N.
  - NeMo Agent Toolkit's custom router measured **4× lower p50 TTFT** and 1.5× higher p50 tokens/s versus default Dynamo routing.
- **SemiAnalysis AgentX v1.0 dataset** (https://inferencex.semianalysis.com/datasets):
  - 393 opt-in Claude Code sessions, each with ≥20 requests; 44% use subagents.
  - **Median input 142K tokens per request, median output 444 tokens per request**; max 990K.
  - Two variants: 1M-context and ≤256K.
  - Replayed with the AgentX harness (a fork of AIPerf): https://github.com/SemiAnalysisAI/agentx-harness
- **Artificial Analysis AA-AgentPerf** (via NVIDIA blog, 2026-06-12: https://developer.nvidia.com/blog/nvidia-achieves-leading-agentic-coding-performance-on-first-agentic-ai-benchmark/):
  - Real agentic coding trajectories with sequence lengths **5K–131K, mean ~27K**, and simulated tool calls with a **~1 s median** delay.
  - The metric is **concurrent agents** meeting an SLO tier.
- **Together AI coding-agent benchmark** (https://www.together.ai/blog/coding-agent-benchmarks):
  - Prompts range **~45K–200K tokens**; outputs average ~450 (p50 293, p99 2,230), roughly **180:1 input:output**.
  - Target: **<1 s TTFT** under load.
- **AIPerf Agentic Code Generator defaults** (https://github.com/ai-dynamo/aiperf/blob/main/docs/tutorials/agentic-code-generator.md):
  - 32K global shared prefix; ~15K session context.
  - About 6K new input tokens per turn (cap 10K); about 1K output per turn (cap 1.5K).
  - Max prompt 167K tokens; agentic/human delay mixture between turns.
- **NVIDIA GPU-sizing blog** (2026-09-01, https://developer.nvidia.com/blog/how-to-size-gpus-for-ai-inference-and-tco-without-overspending):

| Workload | Cached input | New input | Output | TTFT target |
|---|---|---|---|---|
| AI agents | **>128K** | 500–1K | 200–300 | <2 s for the very-long-context agent example |
| Chatbots / copilots | 1K–5K | 2K–8K | 200–800 | <1 s |

### 6.2 Users to concurrency (duty cycle)

**No NVIDIA source gives a users-to-concurrency formula.** The NVIDIA benchmarking blog only says "concurrent requests is not the same as concurrent users" (https://developer.nvidia.com/blog/llm-benchmarking-fundamental-concepts/). Best public proxies:

- **Anthropic's Claude Code team rate-limit guidance** (https://code.claude.com/docs/en/costs). Per-user TPM falls with team size "because fewer users tend to use Claude Code concurrently in larger organizations":

| Team size | TPM per user | RPM per user |
|---|---|---|
| 1–5 | 200–300K | 5–7 |
| 5–20 | 100–150K | 2.5–3.5 |
| 20–50 | 50–75K | 1.25–1.75 |
| 50–100 | 25–35K | 0.62–0.87 |
| 100–500 | 15–20K | 0.37–0.47 |
| 500+ | 10–15K | 0.25–0.35 |

  - Same page: average enterprise spend is ~$13 per developer per active day, and 90% of users stay under $30 per active day.
  - Its `/usage` example shows 6m20s of API time over a 6h33m wall-clock session, **≈1.6% model-busy time for a human-driven session**.
- **Derived rule of thumb (our inference, not an NVIDIA figure):**
  - One active agentic session issues about **3–7 requests per minute** while working (one per tool round-trip of ~1–30 s plus generation time).
  - Each request carries a 20K–150K context but only ~0.5–6K *new* prefill tokens when the cache hits, and ~300–1,000 output tokens.
  - An active agent loop is "in flight" on the GPU roughly **30–60% of wall time**; the rest is tool execution.
  - A *human-supervised* session is active only part of the day. Anthropic's table implies peak-concurrent to seat ratios of about **1:1 for ≤5 users, ~1:2–1:4 for 20–100 users, and ~1:10–1:20 for 500+ users**.
  - **Planning heuristic for a university:** in-flight requests at peak ≈ 0.1–0.2 × enrolled active users for a class lab with everyone working at once (worst case ≈ 0.5–1× during a live workshop — Anthropic explicitly warns about "live training sessions"), and ≈ 0.03–0.1 × for a campus-wide assistant.
  - **Validate with AIPerf trace replay (Weka/AgentX traces or the agentic code generator) and user-centric timing.**

### 6.3 KV cache bytes per token

**Formula** (NVIDIA "Mastering LLM Techniques: Inference Optimization", https://developer.nvidia.com/blog/mastering-llm-techniques-inference-optimization/):
`KV bytes/token = 2 (K and V) × num_layers × (num_kv_heads × head_dim) × bytes_per_elem`.

The blog writes `num_heads`; for GQA models use `num_key_value_heads`.
- **MLA** models (DeepSeek/Kimi/GLM-Flash): `num_layers × (kv_lora_rank + qk_rope_head_dim) × bytes`.
- **Sliding-window** layers: capped at the window size.
- **Mamba/hybrid** layers: a constant per-sequence state, not per token.

Computed from HF `config.json` files (fetched 2026-09-26), BF16 KV (FP8 KV halves these):

| Model | Attention config | KV per token (BF16) | 64K-token session | 128K session |
|---|---|---|---|---|
| gpt-oss-120b | 36 layers (18 full + 18 SWA window 128), 8 KV heads × 64 | **36 KiB** (+4.5 MiB/seq for SWA) | 2.3 GiB | 4.5 GiB |
| Qwen3-32B | 64 L, 8 KV × 128 | **256 KiB** | 16 GiB | 32 GiB (native max 40K without YaRN) |
| Qwen3-Coder-30B-A3B | 48 L, 4 KV × 128 | **96 KiB** | 6 GiB | 12 GiB |
| Qwen3-Coder-480B-A35B | 62 L, 8 KV × 128 | **248 KiB** | 15.5 GiB | 31 GiB |
| Nemotron-3-Nano-30B-A3B | 52 L hybrid: only 6 attention layers, 2 KV × 128 (23 Mamba) | **6 KiB** (+ constant Mamba state) | 0.4 GiB | 0.75 GiB |
| GLM-4.7-Flash (MLA) | 47 L × (512+64) | **~53 KiB** | 3.3 GiB | 6.6 GiB |
| DeepSeek-V3.2 / Kimi-K2 (MLA) | 61 L × (512+64) | **~69 KiB** (35 KiB FP8) | 4.3 GiB | 8.6 GiB |

**Implication.** Concurrent 64K-context agent sessions per GPU are bounded by KV space ≈ (HBM − weights − ~10% activations/overhead) / per-session KV.
- **Qwen3-32B-FP8 on H100 80GB:** ~80 − 33 − 8 ≈ 39 GB free → about **2 sessions at 64K** in BF16 KV, ~4 with FP8 KV.
- **Qwen3-Coder-30B-A3B-FP8 on H200:** ~141 − 31 − 14 ≈ 96 GB → ~15 sessions at BF16 KV.
- **gpt-oss-120b on B300:** ~270 − 63 − 25 ≈ 180 GB → ~75 sessions at 64K.
- This is why **KV-aware routing + host/disk offload** (engine-native offload or LMCache, since KVBM is deprecated) and **GQA/MLA/hybrid models** matter far more than FLOPs for agentic workloads.

## 7. Key risks and gaps to flag to the program owner

1. **KVBM is deprecated (v1.5), with removal targeted for v1.6.** Any lab material on KVBM offload should switch to engine-native offload or LMCache.
2. **AIConfigurator was renamed to AISimulate (v1.5).** Update docs and scripts (`pip install aisimulate`). AISimulate has system data for A100/L40S/RTX PRO 6000, but model coverage varies; there is no GB10/Spark data.
3. **Driver R580+ and CUDA 13** are required for current Dynamo containers. Many university clusters run older drivers.
4. **Slurm is a second-class citizen** in Dynamo docs compared with Kubernetes. Budget time to build sbatch templates (etcd/NATS or file discovery).
5. **Ampere:** use vLLM + Marlin (FP8/MXFP4/INT4) and expect no FP8 compute speed-up. NVFP4 on pre-Blackwell is best-effort, with open correctness bugs.
6. **B300:** the gain is in FP4 and attention. INT8 and FP64 are gutted, so use NVFP4 checkpoints to see the benefit.
7. **Academic Grant Program is closed** right now. Watch the portal for the next CFP; the inference/agents track awards 2× DGX Spark plus up to 30K H100 hours.
8. **Data Flywheel blueprint is deprecated.** Point students to the modular NeMo libraries instead. NeMo Platform (nemo-helix) is new (v0.6.0) and its licensing is unverified.
